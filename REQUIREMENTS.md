# Восстановленные функциональные требования — Investing Demo

## 1. Назначение приложения

Веб-приложение для мониторинга рыночных цен акций через API брокера «Тинькофф Инвестиции». Пользователи могут просматривать список акций, их текущие цены, тренды и исторические графики. Авторизованные пользователи могут управлять каталогом акций (CRUD). Приложение предоставляет REST API для программного доступа к данным.

---

## 2. Основные функциональные возможности

На основании анализа исходного кода выделены следующие функциональные возможности:

1. **Просмотр каталога акций** — пагинированный список с индикацией тренда цены.
2. **Детальная информация об акции** — текущая цена и график исторических данных.
3. **Управление акциями (CRUD)** — добавление, редактирование, удаление (только для авторизованных).
4. **Аутентификация пользователей** — регистрация, вход, выход.
5. **Периодическое обновление цен** — фоновая Celery-задача, обращающаяся к Tinkoff API.
6. **REST API** — программный доступ к каталогу акций с фильтрацией и поиском.
7. **Загрузка каталога из внешнего API** — management-команда для начального заполнения БД.
8. **Django Admin** — административная панель для управления акциями.

5. Пользователь может перейти на другую страницу списка.

**Подтверждение:** `ShareListView` (`dashboard/views.py:20-26`), шаблон `list.html` (условие `{% if user.is_authenticated %}`).

### Сценарий 2: Пользователь открывает детальную страницу акции
1. Пользователь кликает на тикер акции в списке.
2. Система загружает страницу `/ <id>/` с информацией об акции.
3. Отображаются: название инструмента, текущая цена с валютой, время последнего обновления.
4. Отображается график исторических цен за последние 180 дней (линейный график, Plotly).

**Подтверждение:** `ShareDetailView` (`dashboard/views.py:29-38`), `get_graph()` (`dashboard/services/graph.py:11-36`), шаблон `detail.html`.

### Сценарий 3: Гость регистрируется
1. Пользователь переходит на страницу регистрации `/user/registration/`.
2. Заполняет форму: email, пароль, подтверждение пароля.
3. Система проверяет: совпадение паролей, уникальность email.
4. При успешной регистрации создаётся учётная запись и пользователь автоматически авторизуется.
5. Пользователь перенаправляется на главную страницу.

**Подтверждение:** `RegistrationView` (`user/views.py:36-55`), `RegistrationForm` (`user/forms.py:8-51`), шаблон `registration.html`.

### Сценарий 4: Пользователь входит в систему

2. Заполняет форму: email, пароль.

4. При успешном входе пользователь перенаправляется на главную страницу.
5. При неудаче отображается сообщение «Неверный логин или пароль».

**Подтверждение:** `AuthView` (`user/views.py:8-33`), `AuthForm` (`user/forms.py:54-68`), шаблон `auth.html`.

### Сценарий 5: Авторизованный пользователь выходит из системы
1. Пользователь кликает на ссылку «Выход» в навигационном меню.
2. Система завершает сессию и перенаправляет на главную страницу.

**Подтверждение:** `LogoutView` (`user/views.py:58-64`), URL `/user/logout/`.

### Сценарий 6: Авторизованный пользователь добавляет акцию
1. Авторизованный пользователь кликает кнопку «Добавить» на главной странице.
2. Открывается форма создания акции `/create`.
3. Пользователь заполняет поля и отправляет форму.
4. Система сохраняет запись в БД и перенаправляет на главную страницу.

### Сценарий 7: Авторизованный пользователь редактирует акцию
1. Авторизованный пользователь кликает кнопку «Редактировать» напротив акции.
2. Открывается форма редактирования `/update/<id>/` с предзаполненными данными.
3. Пользователь изменяет поля и отправляет форму.
4. Система обновляет запись в БД и перенаправляет на главную страницу.

**Подтверждение:** `ShareUpdateView` (`dashboard/views.py:49-55`), шаблон `create.html` (используется для создания и редактирования).

### Сценарий 8: Авторизованный пользователь удаляет акцию
1. Авторизованный пользователь кликает кнопку «Удалить» напротив акции.
2. Открывается страница подтверждения удаления `/delete/<id>/`.
3. При подтверждении система удаляет запись из БД и перенаправляет на главную страницу.

**Подтверждение:** `ShareDeleteView` (`dashboard/views.py:58-63`), шаблон `delete.html`.

### Сценарий 9: Фоновое обновление цен
1. Celery Beat запускает задачу `update_last_price` каждые 10 секунд.
2. Задача перебирает все акции в БД и для каждой запрашивает последнюю цену через Tinkoff API.
3. Система обновляет поля `last_price` и `is_trend_high` на основе сравнения с предыдущей ценой.
4. Поле `updated_at` автоматически обновляется Django (`auto_now=True`).

**Подтверждение:** `update_last_price()` (`dashboard/tasks.py:7-28`), расписание в `config/celery.py:13-17`, `get_last_data()` (`dashboard/services/market_data.py:6-11`).

### Сценарий 10: Загрузка каталога акций
1. Администратор выполняет команду `python manage.py add_shares`.
2. Система обращается к Tinkoff API и получает полный список доступных акций.
3. Для каждой акции создаётся или обновляется запись в БД (по ключу `figi`).

**Подтверждение:** `dashboard/management/commands/add_shares.py:8-22`.

## 4. Бизнес-правила, проверки и ограничения

### BP-1: Уникальность идентификаторов акции
Поля `figi`, `ticker`, `uid` должны быть уникальными в таблице `Share`. Дублирование запрещено на уровне БД.

**Подтверждение:** `models.py:7` (unique=True), `models.py:10` (unique=True), `models.py:12` (unique=True).

### BP-2: Ограничение доступа к CRUD-операциям
Добавление, редактирование и удаление акций доступно только авторизованным пользователям. Неавторизованные пользователи перенаправляются на главную страницу.

**Подтверждение:** `IsUserAuthenticatedMixin` (`dashboard/views.py:11-17`), `test_func()` возвращает `self.request.user.is_authenticated`.

### BP-3: Визуальная индикация тренда цены
Зелёный фон (`mediumseagreen`) — цена выросла по сравнению с предыдущим значением. Красный фон (`palevioletred`) — цена упала или тренд не определён.

**Подтверждение:** `list.html:35-39` (условие `{% if share.is_trend_high %}`).

### BP-4: Пагинация списка акций
Список акций отображается по 100 записей на страницу с навигацией по страницам.

**Подтверждение:** `ShareListView.paginate_by = 100` (`dashboard/views.py:25`).

### BP-5: Сортировка списка акций
Акции сортируются по алфавиту по полю `name`.

**Подтверждение:** `ShareListView.ordering = ["name"]` (`dashboard/views.py:26`).

### BP-6: Проверка при регистрации
Пароли должны совпадать, email должен быть уникальным. При нарушении — форма возвращает ошибку.

**Подтверждение:** `RegistrationForm.clean()` (`user/forms.py:30-44`).

### BP-7: Автоматическая авторизация после регистрации
После успешной регистрации пользователь автоматически входит в систему.

**Подтверждение:** `RegistrationView.post()` → `login(request, user)` (`user/views.py:47-48`).

### BP-8: Период графика исторических цен
График отображает данные за последние 180 дней с дневным интервалом свечей.

**Подтверждение:** `graph.py:16` (`timedelta(days=180)`), `CandleInterval.CANDLE_INTERVAL_DAY`.

### BP-9: Логика определения тренда
Если текущая цена выше предыдущей — `is_trend_high = True` (рост). Если ниже — `False` (падение).

**Подтверждение:** `tasks.py:15-19` (сравнение `share.last_price > last_price`).

**Примечание:** Реализация содержит дефект — условие инвертировано (см. раздел 6, дефект D-1).

### BP-10: REST API — пагинация и фильтрация
API использует LimitOffset-пагинацию (100 записей по умолчанию), поддерживает фильтрацию по `name` и `ticker`, сортировку по `name`/`ticker`, поиск по `name`.

**Подтверждение:** `settings.py:32-36` (REST_FRAMEWORK config), `ShareFilter` (`api/v1/views.py:10-13`), `ShareViewSet` (`api/v1/views.py:16-22`).

## 5. Функциональные требования

На основании сценариев и бизнес-правил сформулированы следующие функциональные требования:

### FR-1: Просмотр списка акций
Система должна предоставлять любому пользователю (включая неавторизованного) возможность просматривать пагинированный список всех акций с тикером, названием, ISIN и текущей ценой. Цена должна отображаться с цветовой индикацией: зелёный фон — рост, красный — падение. Список должен быть отсортирован по алфавиту (поле `name`), размер страницы — 100 записей.

**Подтверждение:** `ShareListView` (`dashboard/views.py:20-26`), шаблон `list.html`, `IsUserAuthenticatedMixin` не применяется к `ShareListView`.

### FR-2: Детальная информация об акции
Система должна предоставлять любому пользователю возможность открывать страницу акции с текущей ценой, валютой, временем последнего обновления и графиком исторических цен за последние 180 дней (дневные свечи, линейный график Plotly).

**Подтверждение:** `ShareDetailView` (`dashboard/views.py:29-38`), `get_graph()` (`dashboard/services/graph.py:11-36`), шаблон `detail.html`.

### FR-3: Регистрация пользователя
Система должна позволять гостю зарегистрироваться, указав email и пароль (с подтверждением). При регистрации должны проверяться уникальность email и совпадение паролей. После успешной регистрации пользователь должен автоматически авторизоваться.

**Подтверждение:** `RegistrationView` (`user/views.py:36-55`), `RegistrationForm` (`user/forms.py:8-51`), шаблон `registration.html`.

### FR-4: Авторизация пользователя
Система должна позволять пользователю войти по email и паролю. При неудачной попытке должно отображаться сообщение об ошибке.

**Подтверждение:** `AuthView` (`user/views.py:8-33`), `AuthForm` (`user/forms.py:54-68`), шаблон `auth.html`.

### FR-5: Выход из системы
Система должна позволять авторизованному пользователю выйти из системы и перенаправить его на главную страницу.

**Подтверждение:** `LogoutView` (`user/views.py:58-64`).

### FR-6: CRUD акций — только для авторизованных
Система должна позволять авторизованному пользователю добавлять, редактировать и удалять записи об акциях. Кнопки «Добавить», «Редактировать», «Удалить» должны быть видны только авторизованным пользователям. Неавторизованные пользователи должны перенаправляться на главную страницу при попытке доступа к CRUD-операциям.

**Подтверждение:** `IsUserAuthenticatedMixin` (`dashboard/views.py:11-17`), `ShareCreateView` (`views.py:41-46`), `ShareUpdateView` (`views.py:49-55`), `ShareDeleteView` (`views.py:58-63`), шаблон `list.html` (условия `{% if user.is_authenticated %}`).

### FR-7: Периодическое обновление рыночных цен
Система должна автоматически обновлять рыночные цены акций через фоновую задачу Celery Beat с интервалом 10 секунд. Задача должна обращаться к Tinkoff API, получать последние цены и обновлять поля `last_price` и `is_trend_high` для всех акций в БД.

**Подтверждение:** `update_last_price()` (`dashboard/tasks.py:7-28`), `config/celery.py:13-17` (beat_schedule, schedule = 10.0), `get_last_data()` (`dashboard/services/market_data.py:6-11`).

### FR-8: REST API для акций
Система должна предоставлять REST API по адресу `/api/v1/shares/` с поддержкой CRUD-операций (ModelViewSet). API должен поддерживать пагинацию (LimitOffset, 100 записей), фильтрацию по `name` и `ticker`, сортировку по `name`/`ticker`, поиск по `name`.

**Подтверждение:** `ShareViewSet` (`api/v1/views.py:16-22`), `ShareSerializer` (`api/v1/serializer.py:6-19`), `ShareFilter` (`api/v1/views.py:10-13`), `router.py:5-6`, `settings.py:32-36`.

### FR-9: Загрузка каталога акций из Tinkoff API
Система должна предоставлять management-команду `add_shares` для загрузки полного списка доступных акций из Tinkoff Invest API в базу данных. Команда должна использовать `get_or_create` для избежания дублирования записей.

**Подтверждение:** `dashboard/management/commands/add_shares.py:8-22`.

### FR-10: Django Admin панель
Система должна предоставлять административную панель Django для просмотра, поиска и редактирования акций. Поиск должен поддерживаться по полям `figi`, `isin`, `name`, `ticker`.

**Подтверждение:** `ShareAdmin` (`dashboard/admin.py:6-19`), `config/urls.py:5` (admin URL).

## 6. Выявленные неоднозначности, противоречия и дефекты реализации

### Дефекты, влияющие на функциональность

#### D-1: Инвертированная логика определения тренда
В `dashboard/tasks.py:16-19` условие `share.last_price > last_price` устанавливает `is_trend_high = False` при росте и `True` при падении — логика инвертирована. Ожидаемое поведение: `is_trend_high = True` при росте цены.

**Фактическое поведение:** Зелёный фон отображается при падении цены, красный — при росте.

**Подтверждение:** `tasks.py:16-19`.

#### D-2: TypeError при первом обновлении цены
Когда `share.last_price = None` (новая запись), сравнение `share.last_price > last_price` вызывает `TypeError`. Голый `except Exception` молча устанавливает `is_trend_high = True`, что маскирует ошибку.

**Подтверждение:** `tasks.py:15-22`.

#### D-3: CSRF-защита присутствует в шаблонах
Шаблоны `auth.html` и `registration.html` содержат `{% csrf_token %}` — CSRF-защита реализована корректно.

**Подтверждение:** `auth.html:4`, `registration.html:5`.

### Архитектурные и конфигурационные проблемы

#### D-4: Пустой SECRET_KEY
`config/settings.py:6` — `SECRET_KEY = ""`. Приложение не запустится без валидного ключа.

#### D-5: DEBUG = True
`config/settings.py:8` — режим отладки включён, что небезопасно для продакшен-окружения.

#### D-6: Hardcoded пароль БД
`config/settings.py:100` — пароль `postgres` зашит в коде.

#### D-7: Пустой TINKOFF_TOKEN
`config/settings.py:134` — токен API пуст по умолчанию, обновление цен не работает без валидного токена.

#### D-8: Отсутствие аутентификации в REST API
`ShareViewSet` не требует авторизации — любой может читать, создавать, обновлять и удалять акции через API.

**Подтверждение:** `api/v1/views.py:16-22` (нет `permission_classes`).

#### D-9: ShareModelForm exposes все поля
`fields = "__all__"` позволяет пользователю подменять `last_price`, `is_trend_high`, `uid`, `figi` — системные поля, которые должны управляться автоматически.

**Подтверждение:** `dashboard/forms.py:11`.

#### D-10: Частота обновления цен
Celery Beat запускает задачу каждые 10 секунд, что создаёт чрезмерную нагрузку на Tinkoff API. Название задачи `add-every-5-min` не соответствует реальному расписанию.

**Подтверждение:** `config/celery.py:14-16`.

#### D-11: AuthView не использует валидацию формы
`user/views.py:17-19` — `form.data` используется напрямую без `form.is_valid()`, что может вызвать `KeyError` при пустых полях.

#### D-12: docker-compose.yml без Django-сервиса
В compose-файле только PostgreSQL и Redis, нет сервиса для самого приложения и Celery worker/beat.

### Неоднозначности

#### A-1: Модель User без кастомизации
Приложение использует стандартную модель `django.contrib.auth.models.User`, где `username` — обязательное поле. При регистрации `username` устанавливается равным email (`create_user(email, email, password)`). Пользователь вводит только email, но система хранит его и как `username`, и как `email`.

**Подтверждение:** `user/forms.py:49` (`User.objects.create_user(email, email, password)`).

#### A-2: Отсутствие связи пользователь → акции
Модели `Share` и `User` не связаны. Нет понятия «мой портфель» или «мои наблюдения». Все акции доступны всем пользователям одинаково.

**Подтверждение:** `dashboard/models.py` (нет ForeignKey/ManyToManyField к User).

#### A-3: График использует линейный график, а не свечи
Несмотря на то, что данные запрашиваются как дневные свечи (`CandleInterval.CANDLE_INTERVAL_DAY`), график строится как линейный (`Scatter` с `mode="lines"`), используя только `close` цены. Открытие, максимум, минимум игнорируются.

**Подтверждение:** `graph.py:19-20` (`candle.close.units`), `graph.py:26` (`mode="lines"`).

#### A-4: Дублирование кода подключения к Tinkoff API
`Client(TINKOFF_TOKEN)` создаётся отдельно в `market_data.py`, `graph.py` и `add_shares.py` — нет единой точки подключения.

**Подтверждение:** `market_data.py:7`, `graph.py:12`, `add_shares.py:12`.
