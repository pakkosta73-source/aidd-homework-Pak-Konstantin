> Документ восстановлен по фактической реализации (анализ исходного кода: `ANALYSIS.md`,

## 1. Назначение приложения

Веб-приложение для мониторинга рыночных цен акций через API брокера «Тинькофф Инвестиции».
Пользователи просматривают список акций с текущими ценами и трендами, карточки акций
с историческими графиками, получают внутрисайтовые уведомления о достижении целевых
ценовых уровней. Каталог акций администрируется через CRUD-интерфейс, Django Admin
и REST API.

---

## 2. Основные функциональные возможности (обзор)

1. Просмотр пагинированного списка акций с текущей ценой и индикацией тренда.
2. Просмотр карточки акции с графиком исторических цен (180 дней, Plotly).
3. Регистрация, авторизация и выход (вход по email).
4. CRUD-управление каталогом акций (только для авторизованных).
5. Автоматическое периодическое обновление цен и трендов (Celery Beat).
6. Первичная загрузка каталога акций из Tinkoff API (management-команда).
7. REST API `/api/v1/shares/` с CRUD, пагинацией, фильтрацией и поиском.
8. Django Admin для просмотра и редактирования акций.
9. Персональный мониторинг: список наблюдения (watchlist) с целевыми ценами,
   автоматическая проверка условий и внутрисайтовые уведомления, ручной перевзвод алертов.

## 3. Основные сценарии взаимодействия (use cases)

### UC-1. Просмотр списка акций
**Актор:** любой пользователь (в т.ч. неавторизованный).
1. Пользователь открывает главную страницу `/`.
2. Система показывает таблицу «Тикер / Название / ISIN / Текущая цена».
3. Цена подсвечена: зелёный — тренд вверх, красный — тренд вниз / не определён.
4. Список отсортирован по названию, разбит на страницы по 100 записей, есть навигация.

### UC-2. Просмотр карточки акции
**Актор:** любой пользователь.
1. Пользователь открывает страницу акции `/<pk>` из списка.
2. Система показывает текущую цену, время последнего обновления и график
   исторических цен закрытия за последние 180 дней (Plotly).
3. При недоступности API график не отображается, приложение продолжает работу.

### UC-3. Регистрация пользователя
**Актор:** гость.
1. Гость открывает `/user/registration/` и вводит email, пароль и подтверждение.
2. Система проверяет: пароли совпадают; email ещё не зарегистрирован.
3. При успехе — пользователь автоматически авторизуется и перенаправляется на список акций.
4. При ошибке — отображается сообщение (email занят / пароли не совпадают).

### UC-4. Авторизация
**Актор:** зарегистрированный пользователь.
1. Пользователь открывает `/user/login/`, вводит email и пароль.
2. При успехе — вход в систему и переход на список акций.
3. При ошибке — сообщение «Неверный логин или пароль».

### UC-5. Выход
**Актор:** авторизованный пользователь. Открывает `/user/logout/` — сессия завершается,
редирект на список акций.

### UC-6. Управление каталогом акций (CRUD)
**Актор:** авторизованный пользователь.
1. Пользователь авторизуется; видит кнопки добавления/редактирования/удаления акций.
2. Добавление `/create`, редактирование `/update/<pk>`, удаление `/delete/<pk>`
   (с подтверждением).
3. Неавторизованный пользователь кнопок не видит; при прямом обращении к страницам
   CRUD перенаправляется на главную страницу.
4. Управляемые пользователю поля: `figi`, `isin`, `name`, `ticker`, `currency`;
   служебные поля (`last_price`, `is_trend_high`, `uid`, `updated_at`) заполняются
   системой.

### UC-7. Первичная загрузка каталога
**Актор:** администратор (консоль).
1. Администратор выполняет `python manage.py add_shares`.
2. Система запрашивает список акций из Tinkoff API и импортирует их в БД
   (`get_or_create` по `figi`).

### UC-8. Автоматическое обновление цен
**Актор:** планировщик Celery Beat.
1. Каждые 10 секунд запускается задача `update_last_price`.
2. Для каждой акции запрашивается последняя цена через Tinkoff API; ошибки логируются
   в файл `app.logs`.
3. Сохраняется `last_price`; вычисляется тренд `is_trend_high` (новая цена выше
   прежней → рост).
4. По итогам обновления цен выполняется проверка условий наблюдения (UC-10).

### UC-9. Ведение списка наблюдения
**Актор:** авторизованный пользователь.
1. Пользователь открывает `/watchlist/` и добавляет запись: акция, целевая цена,
   направление условия («выше цели» / «ниже цели»).
2. Страница показывает текущую цену акции и статус уведомления.
3. Пользователь может удалить запись.
4. Пользователь может вручную «сбросить» алерт (`POST /watchlist/reset/<pk>/`),
   чтобы он мог сработать повторно.

### UC-10. Уведомления о достижении цели
**Актор:** авторизованный пользователь.
1. После каждого обновления цен система проверяет активные записи наблюдения
   (`notified=False`): условие `above` истинно при `last_price >= target_price`,
   условие `below` — при `last_price <= target_price`.
2. При выполнении условия создаётся внутрисайтовое уведомление, запись помечается
   `notified=True` (повторного уведомления не будет до перевзвода).
3. Пользователь просматривает уведомления на `/notifications/` (новые сверху).

### UC-11. Работа с REST API
**Актор:** внешний клиент / разработчик.
1. Клиент обращается к `/api/v1/shares/` (DRF ModelViewSet, DefaultRouter).
2. Доступны полный CRUD, пагинация LimitOffset (100 записей), фильтрация по `name`
   и `ticker`, поиск по `name`, сортировка по `name`/`ticker`.

### UC-12. Работа в Django Admin
**Актор:** администратор Django.
1. Админ открывает `/admin/`, ищет акции по `figi`, `isin`, `name`, `ticker`,
   просматривает и редактирует их.

## 4. Бизнес-правила, проверки и ограничения

- **BP-1. Уникальность идентификаторов акции:** поля `figi`, `ticker`, `uid`
  уникальны в таблице `Share` (на уровне БД).
- **BP-2. Ограничение доступа к CRUD:** добавление/редактирование/удаление акций
  доступно только авторизованным пользователям (HTML-части); анонимы — только просмотр.
- **BP-3. Визуальная индикация тренда:** зелёный фон (`mediumseagreen`) — цена выросла
  (`is_trend_high=True`); красный (`palevioletred`) — упала или тренд не определён.
- **BP-4. Пагинация списка:** 100 записей на страницу с навигацией.
- **BP-5. Сортировка списка:** по алфавиту по полю `name`.
- **BP-6. Проверки при регистрации:** пароли должны совпадать; email должен быть
  уникальным: при регистрации `username` устанавливается равным email.
- **BP-7. Автологин после регистрации.**
- **BP-8. Период графика:** 180 дней, дневной интервал свечей (визуализируются цены
  закрытия).
- **BP-9. Логика тренда:** `last_price` выше прежней → `is_trend_high=True`, ниже → `False`.
- **BP-10. REST API:** LimitOffset-пагинация (100), фильтры `name`/`ticker`, поиск
  по `name`, сортировка.
- **BP-11. Дедупликация уведомлений:** уведомление о событии отправляется один раз;
  перевзвод — только вручную через `/watchlist/reset/<pk>/` (изменение цели флаг
  `notified` само не сбрасывает).
- **BP-12. Уникальность записи наблюдения:** пара `(user, share)` уникальна — одну
  акцию нельзя добавить в список дважды.
- **BP-13. Проверка условия по направлению:** `above`: `last_price >= target_price`;
  `below`: `last_price <= target_price`; цена `None` пропускается.
- **BP-14. Плановый интервал обновления цен:** каждые 10 секунд (фактическое
  расписание Celery Beat); ошибки внешнего API не прерывают работу приложения,
  а логируются.
- **BP-15. Режим заглушки:** предусмотрена интеграция с Tinkoff API через
  `dashboard/services/tinkoff_client.py` с возможностью включения мок-режима
  (`USE_TINKOFF_MOCK`) вместо реального подключения.

## 5. Функциональные требования (нумерованный список)

Каждое требование подтверждается ссылкой на реализацию в коде.

### Каталог и просмотр акций

- **FR-1. Список акций.** Система должна отображать главную страницу `/` с
  пагинированным (100 записей) списком акций: тикер, название, ISIN, текущая цена;
  сортировка по `name`. Доступно анонимам.
  *Подтверждение:* `ShareListView` (`dashboard/views.py:20-26`), шаблон `list.html`.
- **FR-2. Индикация тренда цены в списке.** Цена должна подсвечиваться зелёным при
  `is_trend_high=True` и красным иначе.
  *Подтверждение:* `list.html` (стили `mediumseagreen`/`palevioletred`).
- **FR-3. Карточка акции.** Система должна отображать страницу `/<pk>`: текущая цена,
  время обновления, Plotly-график цен закрытия дневных свечей за 180 дней.
  *Подтверждение:* `ShareDetailView` (`dashboard/views.py:29-38`), `services/graph.py`.
- **FR-9. Загрузка каталога.** Management-команда `add_shares` должна импортировать
  каталог акций из Tinkoff API (`get_or_create` по `figi`).
  *Подтверждение:* `dashboard/management/commands/add_shares.py`.

### Аутентификация

- **FR-3(аут). Регистрация.** `/user/registration/`: ввод email, пароля и подтверждения;
  проверки совпадения паролей и уникальности email; при успехе — автологин и редирект
  на список акций; хранение email одновременно в `username` и `email`.
  *Подтверждение:* `RegistrationView` (`user/views.py:36-55`), `RegistrationForm`
  (`user/forms.py:8-51`).
- **FR-4(аут). Авторизация.** `/user/login/`: вход по email (username = email) и паролю;
  при ошибке — сообщение «Неверный логин или пароль».
  *Подтверждение:* `AuthView` (`user/views.py:8-33`), `AuthForm`, `auth.html`.
- **FR-5(аут). Выход.** `/user/logout/` завершает сессию и редиректит на список.
  *Подтверждение:* `LogoutView` (`user/views.py:58-64`).

### CRUD акций

- **FR-6. Управление каталогом.** Авторизованные пользователи создают (`/create`),
  редактируют (`/update/<pk>`) и удаляют (`/delete/<pk>`, с подтверждением) акции.
  Неавторизованные редиректятся на главную.
  *Подтверждение:* `IsUserAuthenticatedMixin` (`dashboard/views.py:11-17`),
  `ShareCreateView`/`ShareUpdateView`/`ShareDeleteView` (`views.py:41-63`),
  `ShareModelForm` (`dashboard/forms.py`).

### Фоновая обработка

- **FR-7. Обновление цен.** Celery Beat каждые 10 секунд запускает `update_last_price`:
  последняя цена каждой акции запрашивается через Tinkoff API, сохраняется
  `last_price`, вычисляется `is_trend_high`; ошибки логируются в `app.logs`.
  *Подтверждение:* beat-расписание в `config/celery.py` (задача «add-every-5-min»,
  schedule=10.0), `dashboard/tasks.py`.
- **FR-7.1. Проверка условий наблюдения.** После обновления цен система запускает
  проверку активных записей наблюдения (см. FR-11).
  *Подтверждение:* `_check_watchlist_conditions` (`dashboard/tasks.py:18-54`).

### Мониторинг (watchlist и уведомления)

- **FR-11. Личный список наблюдения.** Авторизованный пользователь ведёт watchlist:
  добавляет (`/watchlist/`) пару «акция + целевая цена + направление» (`above`/`below`),
  удаляет записи, вручную перевзводит алерт (`POST /watchlist/reset/<pk>/`).
  *Подтверждение:* `WatchlistEntry` (`dashboard/models.py`), views
  (`dashboard/views.py:91-133`).
- **FR-11.1. Автопроверка условий.** Для записей с `notified=False` условие должно
  проверяться после каждого обновления цен: `above` — `last_price >= target_price`,
  `below` — `last_price <= target_price`. Цена `None` пропускается.
  *Подтверждение:* `_check_watchlist_conditions` (`dashboard/tasks.py:18-54`).
- **FR-11.2. Уведомления.** При выполнении условия система создаёт внутрисайтовое
  `Notification` и помечает запись `notified=True` (одно уведомление на событие до
  перевзвода). Список уведомлений — `/notifications/`, новые сверху.
  *Подтверждение:* `Notification` (`dashboard/models.py`),
  `NotificationListView` (`dashboard/views.py:136-144`), шаблон `notification_list.html`.

### REST API и админ

- **FR-8. REST API.** `/api/v1/shares/`: полный CRUD (`ShareViewSet`, DRF
  ModelViewSet + DefaultRouter), LimitOffset-пагинация (100), фильтрация по `name`/
  `ticker`, поиск по `name`, сортировка по `name`/`ticker`. Доступ анонимный.
  *Подтверждение:* `dashboard/api/v1/{router,views,serializer,urls}.py`.
- **FR-10. Django Admin.** Модель `Share` зарегистрирована в админке с поиском
  по `figi`, `isin`, `name`, `ticker` и редактированием.
  *Подтверждение:* `dashboard/admin.py`.

### Инфраструктура запуска

- **FR-12. Инфраструктура.** PostgreSQL и Redis поднимаются через `docker-compose.yml`;
  приложение, Celery worker и beat запускаются отдельно (вне Docker).
  *Подтверждение:* `docker-compose.yml` (только postgres + redis), `config/celery.py`.

## 6. Неоднозначности, противоречия и возможные дефекты реализации

> Эти пункты — **не** функциональные требования; они фиксируют расхождения между
> поведением кода и ожидаемым/логичным поведением.

### Неоднозначности

- **A-1. Двойное хранение email.** Пользователь вводит только email, но система
  записывает его и в `username`, и в `email` (`username = email`). Модель пользователя
  — стандартная `django.contrib.auth.models.User`; приложение `user` собственной
  модели не определяет, `AUTH_USER_MODEL` не переопределён.
- **A-2. Нет понятия «владелец» акций.** Каталог общий: любой аутентифицированный
  пользователь может изменить/удалить любую акцию; персонализирован только watchlist.
- **A-3. «Свечи» рисуются как линейный график.** Данные запрашиваются как дневные
  свечи, но строится линия по `close` (Plotly `Scatter`, `mode="lines") — открытые/
  максимальные/минимальные цены не визуализируются.
- **A-4. Дублирование подключения к API.** `Client(TINKOFF_TOKEN)` создается отдельно
  в `market_data.py`, `graph.py` и `add_shares.py` — нет единой точки подключения
  (в скилах это отмечено как устранённое через `services/tinkoff_client.py`;
  в текущем коде ANALYSIS.md фиксировал дублирование).
- **A-5. Название задачи не соответствует расписанию.** Задача названа
  «add-every-5-min», но `schedule=10.0` — фактически 10 секунд.
- **A-6. Проверка цены.** Цена запрашивается как `price.units`, `nano` игнорируется —
  точность до целых рублей (дефект точности, см. D-1). Формально требование

### Противоречия

- **Несогласованность приватности UI и API.** HTML-CRUD закрыт миксином
  аутентификации, но `ShareViewSet` открыт анонимно (`permission_classes` не задан,
  действует AllowAny) — CRUD возможен и без авторизации через API.
- **Тихий редирект вместо отказа в доступе.** `IsUserAuthenticatedMixin.handle_no_permission`
  безусловно редиректит на главную (без 403/страницы логина), включая POST-запросы —
  пользователь не понимает причину отказа.
- **Расписание vs название задачи** (см. A-5): заявленное «раз в 5 минут» фактически
  «каждые 10 секунд каждому брокеру» — чрезмерная нагрузка на Tinkoff API.
- **Отсутствие 404.** `Share.objects.get(id=pk)` в `ShareDetailView` кидает
  `DoesNotExist` → 500 вместо 404 при несуществующем pk.

### Дефекты реализации (зафиксированы, не являются требованиями)

- **D-1. Потеря точности цен.** `market_data.py` и `graph.py` используют только
  `price.units` (рубли), игнорируя `nano` — цены roundятся до целых рублей.
- **D-2. Инвертированная логика тренда.** В `dashboard/tasks.py` при росте цены
  устанавливается `is_trend_high=False` (и наоборот) — цвета индикации в UI
  перепутаны; BP-9/FR-2 фактически нарушаются.
- **D-3. TypeError при первом обновлении.** Если `last_price=None`, сравнение в
  `update_last_price` падает; голый `except Exception` молча помечает акцию растущей
  (`is_trend_high=True`) — дезинформация на UI.
- **D-4. Голые `except Exception`** в `tasks.py` и `graph.py` маскируют реальные ошибки.
- **D-5. `RegistrationForm` — неоценённый queryset.** `User.objects.filter(email=email)`
  в булевом контексте всегда истинен → регистрация всегда падает с «email уже
  зарегистрирован». Фикс: `.exists()` / `.first()`.
- **D-6. `AuthView` не вызывает `form.is_valid()`** перед обращением к `form.data`
  — возможен KeyError.
- **D-7. Отсутствие password-валидаторов при регистрации.** Форма не наследует
  `UserCreationForm`; валидаторы пароля из `settings.py` не применяются; сообщения
  об ошибках достаются через нестандартный `form.errors["__all__"]`.
- **D-8. `ShareModelForm` с `fields = "__all__"`.** Пользователь может вручную
  редактировать служебные/идентификационные поля `last_price`, `is_trend_high`,
  `uid`, `figi`.
- **D-9. Производительность задачи обновления.** N последовательных запросов к API
  (новый gRPC-клиент на каждую акцию) и N отдельных UPDATE каждые 10 секунд.
- **D-10. Некэшируемый запрос истории.** График 180 дней запрашивается синхронно при
  каждом открытии карточки — медленная загрузка, лишняя нагрузка на API.
- **D-11. Безопасность конфигурации.** Пустой `SECRET_KEY`, `DEBUG=True`,
  `ALLOWED_HOSTS=[]`, захардкоженные креды БД и `TINKOFF_TOKEN` в `settings.py`,
  продублированные в docker-compose; логи пишутся в `app.logs` в корне проекта
